# AI_FURNITURE_EXECUTION.md
## Постоянные правила реализации проекта «AI Мебельщик»

> Этот файл задаёт постоянные правила работы Codex и других технических агентов внутри репозитория `ai-furniture-estimator`.
>
> Он не является Wiki-инструкцией и не заменяет `PROJECT_CONTEXT.md` или контекст конкретного этапа.

---

# 1. Назначение

Репозиторий:

```text
C:\Project_all\ai-furniture-estimator
```

Проект:

```text
AI Мебельщик
```

Назначение MVP:

```text
предварительный расчёт кухонной мебели
```

Базовый принцип:

```text
LLM понимает и структурирует.
Детерминированный код проверяет, конфигурирует и рассчитывает.
Google Sheets хранит расчётные данные и результаты.
```

Этот файл отвечает на вопрос:

> Как Codex должен работать в проекте?

Для ответа на вопросы:

> Что это за проект?
> Какой baseline принят?
> Что делать на текущем этапе?

использовать отдельные файлы контекста.

```text
AI_FURNITURE_EXECUTION.md
```


Пример:

```text

```

## 2.4. Принятые отчёты предыдущих этапов

Пример:


Только после изучения контекста этапа.

Если два документа противоречат друг другу, приоритет имеет:

```text
1. более новый явно ACCEPTED / CLOSED stage report;
2. текущий stage context;
3. PROJECT_CONTEXT.md;
4. старые аналитические или промежуточные файлы.
```

При неразрешимом конфликте не угадывать — остановиться и эскалировать Штабу.

---

# 3. Модель управления проектом

Проект использует три режима реализации:

```text
FAST
NORMAL
CONTROLLED
```

Режим задаётся Штабом в контракте текущего этапа.

Если режим явно не указан:

```text
NORMAL
```

является режимом по умолчанию.

---

# 4. FAST

Используется для:

- небольших локальных изменений;
- легко проверяемых задач;
- легко обратимых изменений;
- исправления известной локальной ошибки;
- простого изменения структуры файлов;
- небольшого рефакторинга без изменения архитектуры.

Рабочий цикл:

```text
прочитать контекст
→ выполнить задачу
→ выполнить минимально необходимые проверки
→ исправить ошибки
→ зафиксировать результат
→ кратко отчитаться
```

Не создавать лишние промежуточные документы и отчёты, если они не требуются контрактом.

FAST не означает снижение требований к корректности.

---

# 5. NORMAL

Это основной режим проекта.

Используется для большинства этапов.

Штаб задаёт:

1. цель;
2. baseline;
3. scope;
4. ограничения;
5. ожидаемый результат;
6. acceptance criteria.

Codex самостоятельно:

- исследует текущее состояние репозитория;
- определяет затрагиваемые части;
- составляет внутренний план работы;
- выбирает локальные технические решения;
- создаёт и изменяет необходимые файлы внутри разрешённого scope;
- реализует решение;
- запускает проверки и тесты;
- анализирует ошибки;
- исправляет ошибки;
- повторяет цикл до выполнения acceptance criteria;
- создаёт итоговый отчёт этапа;
- делает итоговый осмысленный Git commit, если это разрешено контрактом.

Рабочий цикл:

```text
контекст
→ план
→ реализация
→ тест
→ ошибка
→ исправление
→ повторный тест
→ acceptance criteria
→ report
→ commit
```

Не запрашивать подтверждение Штаба для обычных локальных технических решений, если:

- они находятся внутри scope;
- не меняют принятую архитектуру;
- не меняют accepted baseline;
- обратимы через Git;
- могут быть проверены тестами или инспекцией.

---

# 6. CONTROLLED

Используется только при явно указанном режиме или после эскалации.

CONTROLLED требуется, если:

- выполняется массовое преобразование или миграция данных;
- меняются критичные правила расчёта;
- затрагивается ключевая архитектура;
- ошибка может быть трудно обнаружима;
- ошибка может распространиться на следующие этапы;
- задача содержит серьёзную методологическую неоднозначность;
- требуется несколько независимых проверок;
- ранее автономная попытка оказалась недостаточно надёжной.

В CONTROLLED Codex:

- не принимает самостоятельно принципиальные архитектурные решения;
- фиксирует неоднозначности;
- выполняет только явно разрешённый следующий блок;
- сохраняет дополнительные доказательства и проверки, если это требует контракт;
- останавливается на контрольных точках, заданных Штабом.

CONTROLLED не означает ручное согласование каждой строки кода.

---

# 7. Когда обязательна эскалация Штабу

Codex должен остановиться и запросить решение, если обнаружено хотя бы одно:

## 7.1. Архитектурная развилка

Есть два или более существенно разных решения, и выбор влияет на будущую архитектуру.

## 7.2. Выход за scope

Для выполнения задачи требуется изменить части проекта, прямо не разрешённые контрактом.

## 7.3. Конфликт baseline

Принятый stage report, `PROJECT_CONTEXT.md`, код или данные противоречат друг другу так, что нельзя определить корректный источник истины.

## 7.4. Необратимый или дорогой риск

Дальнейшее действие может:

- повредить исходные данные;
- вызвать массовое необратимое изменение;
- потребовать внешнего publish/push/deploy;
- изменить пользовательские или производственные данные.

## 7.5. Требуется продуктовое решение

Например:

- что считать допустимой погрешностью;
- какой сценарий поддерживать в MVP;
- какое поведение считать правильным при неоднозначном входе.

Такие вопросы не решать самостоятельно.

---

# 8. Что не является причиной для эскалации

Не обращаться к Штабу только потому, что:

- тест упал;
- возникла ошибка компиляции;
- найден локальный баг;
- требуется переименовать внутреннюю функцию;
- нужно добавить тест;
- требуется небольшой рефакторинг;
- выбранный локальный технический подход не сработал с первой попытки.

Сначала самостоятельно пройти цикл:

```text
ошибка
→ анализ
→ исправление
→ повторная проверка
```

Эскалировать только после нескольких разумных попыток или при переходе проблемы в одну из категорий раздела 7.

---

# 9. Границы проекта

Без отдельного разрешения нельзя:

- менять продуктовую концепцию;
- расширять MVP за пределы кухонь;
- добавлять Supabase;
- добавлять Vercel;
- добавлять отдельную SQL-базу;
- добавлять отдельный облачный backend;
- добавлять RAG / embeddings / vector DB;
- добавлять сложный каскад агентов;
- менять LLM на источник расчётной стоимости;
- переносить детерминированные расчёты в LLM;
- начинать следующий этап раньше завершения текущего;
- выполнять publish / deploy / push.

Дополнительные ограничения текущего этапа задаются его `stage-X-context.md`.

---

# 10. Работа с source-materials

Папка:

```text
source-materials/
```

содержит исходные и эталонные материалы.

По умолчанию:

```text
READ ONLY
```

Нельзя изменять исходные Excel, PDF, PNG, DOCX, ZIP и другие первичные материалы, если контракт этапа явно не разрешает обратное.

Разрешено добавлять в `source-materials/` отдельные утверждённые reference datasets, если это прямо принято Штабом.

Не заменять исходные данные «исправленной» версией без отдельного решения.

---

# 11. Accepted baseline

Файл или результат со статусом:

```text
ACCEPTED
ACCEPTED WITH DEBT
CLOSED
```

считается принятым baseline.

Нельзя менять accepted baseline для удобства реализации следующего этапа.

Если новый этап выявляет ошибку в baseline:

```text
остановиться
→ описать проблему
→ указать влияние
→ предложить варианты
→ ждать решения Штаба
```

---

# 12. Git

Перед существенной работой проверить:

```text
git status --short
git branch --show-current
```

Перед итоговым commit:

```text
git diff --check
git diff --stat
git status --short
```

Правила:

- не выполнять `push` без отдельного разрешения;
- не переписывать историю без отдельного разрешения;
- не делать destructive reset без отдельного разрешения;
- не включать случайные несвязанные изменения в commit;
- commit должен соответствовать одному осмысленному этапу или исправлению;
- после завершения этапа working tree должен быть чистым, если контракт не говорит обратное.

---

# 13. Отчёт этапа

Для этапов в режиме NORMAL и CONTROLLED Codex должен создавать локальный отчётный Markdown-файл.

Пример:

```text
docs/stage-3-calculation-model/stage-3.3-report.md
```

Отчёт является постоянным техническим артефактом проекта и используется:

- Штабом для приёмки;
- следующим этапом как расширенный контекст;
- для восстановления истории решений;
- для анализа проблем без чтения полного Git diff.

Отчёт не должен быть журналом всех действий.

Минимальная структура:

```markdown
# Этап X — Отчёт

## Статус
COMPLETE / PARTIAL / BLOCKED

## Что реализовано

## Ключевые решения

## Проверки и тесты

## Ограничения / открытые вопросы

## Git
- branch
- commit
- working tree
- push
```

Если контракт этапа задаёт более точную структуру, использовать её.

---

# 14. Контекст следующего этапа

Codex не создаёт контракт следующего этапа, если это отдельно не поручено.

После текущего этапа:

```text
Codex
→ stage-X-report.md
→ Штаб
→ ACCEPT / CORRECT
→ новый stage-X+1-context.md
```

Только Штаб определяет следующий этап и его scope.

---

# 15. Минимализм артефактов

Не создавать файлы «на будущее».

Не создавать автоматически:

- TODO-файлы;
- альтернативные context-файлы;
- дубли отчётов;
- временные схемы;
- многочисленные debug-файлы;
- placeholder-документы.

Временные рабочие файлы после завершения удалить, если они не являются воспроизводимым полезным артефактом.

---

# 16. Проверяемость результата

Предпочитать решения, которые можно проверить:

- автоматическим тестом;
- детерминированным сравнением;
- схемой валидации;
- воспроизводимой командой;
- явным provenance данных.

Не заменять проверяемое правило экспертным текстом, если правило можно формализовать.

Не считать количество выполненных действий показателем качества.

Главный критерий:

```text
acceptance criteria выполнены
и результат воспроизводим
```

---

# 17. Работа с неоднозначностью

Никогда не превращать отсутствие данных в скрытое предположение.

Использовать явные состояния вроде:

```text
UNRESOLVED
NOT_SUPPORTED
REQUIRES_EXPERT
NO_VALID_LAYOUT
```

если это соответствует контракту этапа.

Лучше честно вернуть отсутствие доказанного решения, чем создать удобное, но недоказанное правило.

---

# 18. Модель и reasoning

Выбор модели и уровня reasoning выполняет человек/Штаб перед запуском Codex.

Рекомендуемый профиль указывается в `stage-X-context.md`.

Типовая логика:

```text
простые файловые/структурные операции
→ лёгкий профиль

обычное программирование, парсеры, локальная бизнес-логика
→ средний reasoning

сложные алгоритмы, расчётные правила, архитектурно значимая логика
→ высокий reasoning
```

Codex не должен менять продуктовую архитектуру только потому, что запущен на более сильной модели.

---

# 19. Приоритет качества

При конфликте между:

```text
скоростью
экономией лимита
простотой реализации
доказательностью
```

приоритет:

```text
1. корректность;
2. доказательность;
3. воспроизводимость;
4. минимальная сложность;
5. скорость.
```

При этом не усложнять систему без необходимости.

---

# 20. Финальное правило

Codex управляет своей технической реализацией самостоятельно внутри разрешённых границ.

Штаб управляет:

```text
целями
границами
baseline
риском
acceptance criteria
приёмкой
```

Codex управляет:

```text
декомпозицией
локальными техническими решениями
реализацией
тестами
исправлениями
Git commit
stage report
```

Главный принцип проекта:

```text
не контролировать каждое действие;
контролировать границы, качество и конечный результат.
```
