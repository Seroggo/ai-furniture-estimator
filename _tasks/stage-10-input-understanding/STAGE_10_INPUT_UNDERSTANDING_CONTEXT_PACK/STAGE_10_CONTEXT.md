# Stage 10 — Input Understanding and Confirmation

## Назначение

Stage 10 создаёт локальный входной слой между пользовательскими материалами и существующим `Confirmed Configuration`, которое затем передаётся в Construction Core.

Целевая цепочка:

```text
image / sketch / drawing / text / dimensions
→ Evidence
→ Draft Configuration
→ Clarification
→ User Confirmation
→ Confirmed Configuration
→ Construction Core
```

Главная задача Stage 10 — не рассчитывать мебель, а получить из неполного и разнородного ввода пользователя подтверждённый структурированный JSON.

## Основные принципы

1. Каждый существенный факт должен иметь источник.
2. Явно указанные пользователем размеры сохраняются без нормализации.
3. Неопределённость представляется явно: `MISSING`, `CONFLICT`, `NEEDS_CONFIRMATION`.
4. Значения по умолчанию являются кандидатами до подтверждения.
5. Construction Core получает только `Confirmed Configuration`.
6. Один и тот же подтверждённый JSON должен приводить к одному и тому же расчёту.

## Подэтапы

### 10.1 — Input / Evidence Contract

Определить форматы `Evidence[]`, `Draft Configuration` и детерминированный переход в существующий `Confirmed Configuration`.

Зачем: все последующие части Stage 10 должны обмениваться данными через один устойчивый контракт.

### 10.2 — Clarification Engine

По Draft определить известные значения, пробелы, конфликты и кандидаты по умолчанию.

Зачем: отделить продуктовые правила уточнения от Vision и LLM.

### 10.3 — Vision Recognition MVP

Преобразовывать изображение в структурированные evidence: сущности, взаимное расположение и читаемые размерные подписи.

Зачем: получить факты из изображения, не смешивая распознавание с расчётом.

### 10.4 — Evidence Fusion

Объединять evidence из текста, размеров, изображения и пользовательских подтверждений в единый Draft.

Зачем: несколько источников могут описывать одно поле по-разному, поэтому нужен единый механизм выбора и фиксации конфликтов.

### 10.5 — Dynamic Brief / Confirmation

Формировать короткий бриф только по незакрытым полям и принимать ответы пользователя.

Зачем: довести Draft до полностью подтверждённого входа без длинной фиксированной анкеты.

### 10.6 — Confirmed Configuration → Construction Core

Проверить границу между новым входным слоем и существующим Construction Core.

Зачем: гарантировать, что подтверждённые значения без скрытых преобразований доходят до расчётного ядра.

### 10.7 — Local End-to-End Alpha

Собрать локальную вертикаль от пользовательского ввода до запуска Construction Core на нескольких сценариях.

Зачем: доказать работоспособность Stage 10 целиком до общей интеграции и деплоя.

## Граница Stage 10

Stage 10 завершается локальным E2E PASS.

Интеграция с Web/Apps и общий деплой выполняются позднее единым пакетом вместе с Construction Core и Vision.
