## Что реализовано

Создан минимальный воспроизводимый Python PoC детерминированного компоновщика прямого кухонного ряда:

```text
calculation_model/layout_configurator.py
tests/test_layout_configurator.py
```

Компоновщик:

- читает размерные правила непосредственно из принятого `source-materials/kitchen-module-reference-comparison.csv`;
- различает классы `base`, `wall` и `tall` и не переносит ширину между классами без семантического основания;
- сначала разрешает обязательные функциональные модули, appliance slots и позиционные запреты;
- подбирает только точные подтверждённые ширины соответствующего `module_class`;
- возвращает упорядоченные модули/слоты с ролью, шириной, market rank и `record_id` правила;
- представляет допустимый остаток отдельной сущностью `Filler`;
- возвращает явные `NO_VALID_LAYOUT`, `INVALID_INPUT` или `NOT_SUPPORTED`, а не изобретает размер.

Исходные файлы и принятые данные Этапов 2, 3.1 и 3.2 не изменялись. Следующий расчётный слой не реализован.

## Формальная логика компоновщика

1. Валидировать длину, filler policy, обязательные модули, ограничения позиций и лимиты количества модулей.
2. Для непрямого ряда вернуть `NOT_SUPPORTED`: автоматическая угловая геометрия без явного системного профиля не строится.
3. Определить generic-класс зоны: `base_general`, `wall_general` или `tall_universal`.
4. Разрешить каждый обязательный модуль только по точному PRIMARY market-правилу его собственного `module_class`.
5. Отклонить обязательный модуль из другой зоны, неизвестную ширину и generic-ширину ранга D без точного явного разрешения.
6. Сформировать generic-кандидаты только из точных PRIMARY-ширин нужного класса с автоматическими рангами A/B/C. D/E не используются автоматически.
7. Перебрать неповторяющиеся мультимножества допустимых ширин в пределах свободной длины.
8. Оставить только варианты, которые выполняют mandatory/fixed/forbidden constraints и явные границы filler.
9. Для каждого варианта детерминированно расставить модули с учётом фиксированных и запрещённых позиций.
10. Выбрать минимум по ключу:

```text
(count(E), count(D), count(C), count(B),
 filler_mm,
 explicit_low_rank_generic_count,
 module_count,
 stable_ordered_signature)
```

Hard constraints и семантическая допустимость проверяются до этого ключа и поэтому не могут быть нарушены оптимизацией.

Для Case A такой порядок выбирает `800 + 600 + 600 + 600 = 2600` и отдельный filler 50 мм: комбинация с нулевым остатком требует большего числа более слабых B-ширин.

## Ключевые решения

- Канонический CSV читается во время выполнения; копия или собственная размерная сетка не создавались.
- В автоматическую сетку входят только `record_type=market_baseline`, `source_layer=PRIMARY`, точные `width`/`nominal_width`. Qwen supplement не повышается до PRIMARY и не переопределяет принятые ранги.
- `base_narrow_cargo=150` допустим как обязательная специализированная роль по `MKT-044`; 150 мм не появляется как automatic `base_general`.
- Явное разрешение низкоранговой generic-ширины задаётся точным значением `explicit_generic_widths_mm`, а не широким переключателем всех D/E-размеров.
- Filler разрешается только через `FillerPolicy(min_width_mm, max_width_mm, location)`. Значение 50 мм не является значением по умолчанию или универсальным нормативом.
- `STUDIO_STANDARD` не введён. Более старый `studio-module-analysis.md` не имеет substantive-конфликта с принятым `stage-3.2-report.md`; текущим baseline статуса и выводов считается отчёт 3.2.
- Стандартная библиотека Python выбрана как минимальный runtime без Apps Script, Google Sheets и внешних зависимостей.

## Вход / выход

Вход `LayoutRequest` выражает:

- `run_length_mm`, `run_shape`, `zone`;
- обязательные `RequiredModule` с ролью, `module_class`, шириной и необязательной фиксированной позицией;
- `PositionConstraint` с запрещёнными ролями, классами и ширинами для позиции;
- явную `FillerPolicy`;
- глобально запрещённые и точно разрешённые низкоранговые generic-ширины;
- минимальное/максимальное количество модулей.

Выход `LayoutResult` содержит:

- статус;
- упорядоченные `LayoutItem` для модулей и appliance slots;
- роль, класс, ширину, market rank и provenance каждого элемента;
- занятую длину, остаток, покрытую длину;
- отдельный `Filler` либо `None`;
- причины выбора или отсутствия решения;
- стабильный selection key и источник market baseline.

`LayoutResult.as_dict()` даёт JSON-serializable представление без привязки к будущей Google Sheets schema.

## Проверенные сценарии

- A — 2650 мм: `800 + 600 + 600 + 600`, filler 50 мм.
- B — 2400 мм: обязательный 600-мм ПММ-слот `MKT-030` сохранён на фиксированной позиции.
- C — остаток 150 мм не превращается в cargo или generic-модуль.
- D — обязательный `base_narrow_cargo=150` разрешается по `MKT-044`.
- E — невозможная точная композиция возвращает `NO_VALID_LAYOUT`.
- F — десять повторов одинакового входа дают идентичный сериализованный результат.
- Отдельно: отсутствие универсальной 50-мм filler policy, жёсткий позиционный запрет, перестановка для выполнения запрета, межзонный конфликт классов, фильтрация supplement-слоя, точное разрешение D-ширины, неизвестная ширина, invalid input, лимит модулей и unsupported corner.

## Неподдерживаемые случаи

- угловые, Г-/П-образные и иные непрямые ряды без явного профиля мебельной системы;
- произвольные кастомные ширины, отсутствующие в принятом market baseline;
- автоматический вывод ширины модуля из размеров детали, фасада, столешницы или физического прибора;
- высоты, глубины, ниши и двухмерные footprint-геометрии;
- BOM, детали, материалы, кромка, фурнитура, работы, цены и историческая калибровка;
- Google Sheets schema, Apps Script, Web App, OpenRouter, PDF и full backtest.

Эти границы возвращаются явно или остаются вне входной модели 3.3; скрытые допущения не создаются.
