# AI Мебельщик — Этап 3.3
## Контракт: детерминированный компоновщик кухонных модулей

## 1. Режим выполнения

```text
Управление: NORMAL
Рекомендуемый Codex: GPT-5.6 Sol
Reasoning: High
```

Причина: задача содержит проектирование детерминированного алгоритма и приоритетов выбора, где скрытая логическая ошибка может повлиять на следующие части расчётной модели.

Штаб задаёт цель, baseline, ограничения и критерии готовности. Codex самостоятельно исследует репозиторий, декомпозирует работу, выбирает локальные технические решения, реализует PoC/проверки и исправляет ошибки до выполнения acceptance criteria.

Эскалировать только продуктовую/архитектурную развилку, необходимость выйти за scope или конфликт с принятым baseline.

## 2. Цель

Спроектировать и доказать минимальную детерминированную модель компоновки кухонного ряда:

```text
доступная длина ряда
+ обязательные функциональные модули
+ фиксированные ограничения
+ внешний market baseline
        ↓
валидная последовательность модулей
        ↓
остаток / filler
+ объяснение результата
```

Результат 3.3 должен стать формальным входом для следующего слоя Этапа 3:

```text
modules
→ parts
→ materials
→ hardware
→ works
```

Но сам этот переход на 3.3 не реализуется.

## 4. Принятый baseline 3.1–3.2

### Market baseline

Использовать внешний справочник как источник допустимых и приоритетных размерных классов.

Не превращать одну общую таблицу ширин в универсальную сетку для всех модулей.

Семантика `module_class` и `dimension` обязательна.

### Studio evidence

Принято:

```text
доказанные визуальные section_width: 450 / 600 / 900 мм
600 мм: 9 секций / 2 проекта
600-мм слот ПММ: MARKET_STANDARD
STUDIO_STANDARD: не доказан
```

Следствие:

```text
не вводить дополнительный приоритет "так делает студия"
```

если он не доказан отдельным правилом.

## 5. Scope 3.3

Нужно определить минимальную модель.

### Вход

Как минимум должна быть способна выразить:

- длину доступного прямого ряда;
- тип ряда/зоны, если он влияет на допустимые классы модулей;
- обязательные функциональные модули;
- фиксированные appliance slots;
- фиксированные или запрещённые позиции, если они заданы;
- разрешённую политику filler/компенсационного остатка;
- явно заданные ограничения проекта.

Codex может предложить более точную минимальную схему входа, если она остаётся простой и не тащит в 3.3 будущую архитектуру Apps Script/Google Sheets.

### Выход

Как минимум:

- упорядоченный список модулей/слотов;
- роль;
- ширина;
- источник размерного правила;
- суммарная занятая длина;
- остаток;
- filler, если разрешён;
- статус валидности;
- причины выбора;
- причины отсутствия решения, если валидной комбинации нет.

## 6. Жёсткие правила

### 6.1. Hard constraints выше оптимизации

Обязательный модуль, техника, фиксированное положение или явно заданный технологический запрет нельзя нарушать ради красивой размерной комбинации.

### 6.2. Не использовать `STUDIO_STANDARD`

Такого baseline нет.

### 6.3. Семантика market baseline обязательна

Размер специализированного модуля нельзя автоматически использовать как generic storage только потому, что он помогает закрыть остаток.

Например:

```text
150 мм cargo
```

не должен автоматически вставляться как обычная секция для устранения остатка 150 мм.

### 6.4. D/E не являются автоматическим общим стандартом

Размеры ранга `D` использовать только при совпадении специализированной роли или явном разрешении.

`E` не использовать автоматически.

### 6.5. Нестандартную произвольную ширину не изобретать

Если допустимой комбинации нет, система должна уметь вернуть:

```text
NO_VALID_LAYOUT
```

или эквивалентный результат вместо создания неподтверждённого модуля.

### 6.6. Filler — отдельная сущность

Не считать остаток автоматически мебельным модулем.

Не hardcode универсальные 50 мм: Этап 3.1 не доказал 50 мм как мировой минимум или универсальный норматив.

Допустимая величина filler должна задаваться явной политикой/ограничением.

### 6.7. Техника

600-мм слот ПММ подтверждён как `MARKET_STANDARD`.

Market baseline содержит и другие appliance classes. Использовать их только в соответствующей семантике.

### 6.8. Углы

Угловая геометрия system-specific.

Не изобретать универсальную формулу углового модуля.

Если для PoC нет явного профиля угловой системы, корректный результат — оставить углы вне автоматической компоновки и зафиксировать это как границу 3.3.

## 7. Приоритеты выбора

Предпочтителен детерминированный и объяснимый порядок критериев, а не набор произвольных magic weights.

Рекомендуемая логика:

```text
1. выполнить hard constraints;
2. использовать допустимые размеры соответствующего module_class;
3. предпочитать более сильный market rank;
4. минимизировать технологический остаток / filler в разрешённых пределах;
5. минимизировать использование низкоприоритетных и specialized размеров без необходимости;
6. при прочем равенстве предпочитать более простую композицию / меньше модулей;
7. обеспечить стабильный tie-break, чтобы одинаковый вход всегда давал одинаковый результат.
```

Codex может уточнить порядок после анализа edge cases, но любое изменение должно быть объяснено в отчёте.

Не подменять производственную технологичность дизайнерской модой.

## 8. Базовые проверочные сценарии

Codex должен создать воспроизводимые тестовые сценарии и расширить их edge cases.

### Case A — рациональная комбинация

```text
run_length = 2650
allowed_filler_max = 50
```

При доступности подходящих market widths система должна предпочесть валидную сильную комбинацию с остатком 50 мм, например:

```text
600 + 600 + 600 + 800 = 2600
filler = 50
```

если она побеждает альтернативы по формальным приоритетам.

Этот пример не является hardcoded ответом алгоритма: тест должен проверять именно формализованные критерии выбора.

### Case B — обязательный слот ПММ

```text
run_length = 2400
required:
  dishwasher_slot = 600
allowed_filler_max = 0
```

Результат обязан сохранить 600-мм слот ПММ и подобрать остальные секции только вокруг него.

### Case C — specialized width не используется как generic

Сценарий с остатком, равным специализированной ширине 150/200 мм, не должен автоматически вставлять cargo, если роль cargo не запрошена.

### Case D — разрешённый specialized module

Если `cargo=150` явно указан как обязательный функциональный модуль и market baseline подтверждает такую роль, компоновщик должен уметь использовать его.

### Case E — нет решения

При hard constraints и filler policy, для которых невозможно получить допустимую композицию, должен возвращаться детерминированный `NO_VALID_LAYOUT`, а не произвольный нестандартный модуль.

### Case F — детерминизм

Одинаковый вход должен давать одинаковый результат.

2. минимальная структура входа/выхода;
3. воспроизводимый PoC или иной машинно проверяемый механизм, достаточный для доказательства правил;
4. автоматические тесты основных и граничных сценариев;


Codex может создать дополнительные артефакты только если они реально нужны для результата и не являются заглушками.

## 12. Acceptance criteria

Этап 3.3 считается `COMPLETE`, если:

- market baseline читается из принятого локального источника или его детерминированного представления;
- module classes не смешиваются без семантического основания;
- mandatory modules/hard constraints имеют абсолютный приоритет;
- specialized width не используется как generic без разрешения;
- filler не превращается в модуль;
- filler policy не основана на недоказанном универсальном 50 мм;
- произвольные нестандартные ширины не создаются автоматически;
- отсутствие решения обрабатывается явно;
- результат детерминирован;
- базовые сценарии A–F и дополнительные edge cases проходят;
- углы либо корректно поддержаны по явному профилю, либо честно исключены из автоматического MVP 3.3;
- не введён недоказанный `STUDIO_STANDARD`;
- следующий расчётный слой не реализован;
- исходные данные не изменены;
- `git diff --check` проходит;
- тесты проходят;
- итоговый отчёт создан;
- working tree после итогового коммита чист;
- push не выполнялся.
